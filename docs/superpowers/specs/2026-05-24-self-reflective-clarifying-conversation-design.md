# Self-Reflective Clarifying Conversation — Design

Date: 2026-05-24
Status: Draft — pending user review
Branch: `guoqing`

## 1. Problem

Today the backend takes a one-shot natural-language query (e.g. `"My forehand
is weak"`) and immediately generates a training plan. The current
[backend/app/services/llm.py](../../../backend/app/services/llm.py) prompt
explicitly tells Gemini *"Do not ask follow-up questions; produce the best
useful plan from the available information."* The plan is therefore only as
personalized as the user's single sentence allows — usually not very.

We want the LLM to perform **gap-driven self-reflection**, asking a small
number of high-quality clarifying questions before committing to a plan, so
that the final plan and drills are anchored in specifics (skill level,
symptom, frequency, practice context) rather than fallback assumptions.

## 2. Goals & Non-Goals

### Goals
- Replace the single-shot interaction (for callers who want it) with a short
  multi-turn dialogue, **~3 turns typical, hard cap at 4 turns**, that
  collects the highest-impact missing details.
- Each clarifying question is generated by the LLM after it silently drafts a
  tentative plan and identifies the single biggest gap that would change that
  draft.
- Final plan generation uses the enriched, clarified context — so retrieval
  is sharper and the LLM has real personalization signal to work with.
- Conversation state is persisted in SQLite so we can later audit question
  quality and link conversations to journals.
- Backward compatible: the existing `POST /api/v1/plans` single-shot endpoint
  keeps working unchanged.

### Non-Goals
- No persistent user profile across conversations. Each conversation starts
  fresh. (Future work could add a `User` model that conversations belong to.)
- No frontend work — this spec is backend-only. A CLI REPL gives us a local
  smoke surface.
- No formal eval harness for question quality in this round (we ship the
  diagnostic `reflection_meta` JSON on each assistant message so we can
  inspect runs manually and build evals later).
- No model-based reranker, no provider swap, no Postgres migration.

## 3. Design Decisions (locked during brainstorm)

| Decision | Choice | Rationale |
|---|---|---|
| Interaction surface | Multi-turn conversation | User wants real personalization, not a fixed form |
| Turn budget | ~3 typical, hard cap at 4 | Saves compute and user time |
| Questions per turn | 1 focused question | Low cognitive load, conversational |
| Reflection style | Gap-driven (silent draft → biggest gap → ask) | Anchors questions in what would actually change the plan |
| State management | Server-side SQLite (`Conversation` + `Message` tables) | Plays well with future journaling, lets us audit quality |
| RAG timing | Twice — light at start (`k=3`), full at end (`k=4`) with enriched query | Best quality / cost trade — questions are informed by docs, final plan benefits from sharper retrieval |
| API shape | New `/conversations` endpoints; keep `/plans` single-shot untouched | Two clearly separate flows, no migration risk |
| Stop condition | LLM decides per turn (`action: "ask" \| "generate"`); turn cap forces `"generate"` | Can short-circuit when query is already detailed; cap guarantees termination |
| Per-turn LLM structure | Single structured-output call returning `{draft, gap, action, question}` | Cheapest of the three reflection variants — appropriate for the POC |

## 4. Architecture

```
Client                Backend                              Gemini / Chroma
  │  POST /conversations {initial_query}                       │
  ├─────────────────────────────────────────►                  │
  │                     ConversationService.start              │
  │                     │ 1. Create Conversation + user Msg    │
  │                     │ 2. VectorService.search (k=3, light) ├──► Chroma
  │                     │ 3. ReflectionService.next_step       ├──► Gemini
  │                     │    → {action:"ask", question}        │
  │                     │ 4. Persist assistant Msg             │
  │  ◄──── {needs_answer, question, conversation_id, turn:0}   │
  │                                                            │
  │  POST /conversations/{id}/messages {reply}                 │
  ├─────────────────────────────────────────►                  │
  │                     ConversationService.reply              │
  │                     │ 1. Append user Msg                   │
  │                     │ 2. ReflectionService.next_step       ├──► Gemini
  │                     │    (force_generate when              │
  │                     │     turn_count == max_turns - 1)     │
  │                     │ 3a. action=ask → persist + return    │
  │                     │ 3b. action=generate:                 │
  │                     │     - build enriched_query           │
  │                     │     - VectorService.search (k=4)     ├──► Chroma
  │                     │     - LLMService.generate_plan       ├──► Gemini
  │                     │     - persist TrainingPlan + Drills  │
  │                     │     - link to Conversation, mark done│
  │  ◄──── {plan_ready, plan, conversation_id}                 │
```

### Component responsibilities

- **`ReflectionService`** (new, isolated, no DB or HTTP coupling): given
  conversation history + light retrieved context, returns one
  `ReflectionStep`.
- **`ConversationService`** (new): orchestrator. Owns turn counting,
  state transitions, the flip from "ask" to "generate" mode, and final
  plan persistence.
- **`LLMService.generate_training_plan`** (existing): unchanged. Receives
  an enriched query string at the final step.
- **`VectorService`** (existing): unchanged; called twice with different `k`.
- **CRUD** (new): thin SQLModel ops for `Conversation` and `Message`.
- **API router** (new): three endpoints under `/api/v1/conversations`.

## 5. Data Model

Two new tables in
[backend/app/models/models.py](../../../backend/app/models/models.py):

```python
class Conversation(SQLModel, table=True):
    id: Optional[int] = Field(default=None, primary_key=True)
    status: str = Field(default="active")  # "active" | "completed" | "abandoned"
    turn_count: int = Field(default=0)     # number of LLM "ask" turns so far
    initial_query: str
    training_plan_id: Optional[int] = Field(default=None, foreign_key="trainingplan.id")
    created_at: datetime = Field(default_factory=datetime.utcnow)
    updated_at: datetime = Field(default_factory=datetime.utcnow)
    messages: List["Message"] = Relationship(back_populates="conversation")

class Message(SQLModel, table=True):
    id: Optional[int] = Field(default=None, primary_key=True)
    conversation_id: int = Field(foreign_key="conversation.id")
    role: str               # "user" | "assistant"
    content: str            # the visible question or reply
    turn_index: int         # 0-based position in conversation
    reflection_meta: Optional[str] = None
    # JSON string for assistant rows: {internal_draft, biggest_gap, action}.
    # Lets us audit question quality post-hoc.
    created_at: datetime = Field(default_factory=datetime.utcnow)
    conversation: Conversation = Relationship(back_populates="messages")
```

Alembic migration adds both tables. `TrainingPlan` and `Drill` are unchanged.

## 6. API Contract

New router [backend/app/api/v1/conversations.py](../../../backend/app/api/v1/conversations.py)
mounted at `/api/v1`.

```
POST /api/v1/conversations
  body:     { "initial_query": str (3..1000 chars) }
  201 →     ConversationTurn

POST /api/v1/conversations/{conversation_id}/messages
  body:     { "reply": str (1..1000 chars) }
  200 →     ConversationTurn
  404 →     conversation not found
  409 →     conversation already completed

GET /api/v1/conversations/{conversation_id}
  200 →     ConversationRead  (full transcript + status + linked plan_id)
  404 →     not found
```

`ConversationTurn` is a discriminated union on `status`:

```python
# status == "needs_answer"
{
  "status": "needs_answer",
  "conversation_id": 42,
  "question_number": 2,       # 1-indexed; "Question 2 of 3"
  "max_questions": 3,
  "question": "Does it sail long mostly under pressure or all the time?"
}

# status == "plan_ready"
{
  "status": "plan_ready",
  "conversation_id": 42,
  "plan": TrainingPlanRead   # same schema as POST /api/v1/plans returns today
}
```

`ConversationRead` is a flat view: id, status, turn_count, initial_query,
training_plan_id, created/updated_at, and the full ordered list of messages.

### Turn semantics (definitive)

To eliminate ambiguity between settings, code, and prompts:

- `conversation_max_turns: int = 4` — total reflection-step budget. Each
  reflection step produces either `action="ask"` or `action="generate"`.
  Because the last reflection step is always forced to `"generate"`, this
  caps the number of *clarifying questions* at **3** (steps 0, 1, 2 may ask;
  step 3 always generates).
- `Conversation.turn_count` = number of reflection steps that produced
  `action="ask"` so far. Starts at 0; increments only after a successful
  ask. Does not increment on the final generate step.
- Force-generate triggers when `turn_count == conversation_max_turns - 1`
  (i.e., 3 asks already done → the next reflection must generate).
- API exposes `question_number = turn_count + 1` (1-indexed for humans) and
  `max_questions = conversation_max_turns - 1`. Frontend can render
  "Question N of 3" cleanly.

Error mapping mirrors the existing
[backend/app/api/v1/plans.py](../../../backend/app/api/v1/plans.py)
conventions (`ValueError → 400`, `RuntimeError → 503`).

## 7. Reflection Prompt — the heart of "high quality"

New file [backend/app/services/reflection.py](../../../backend/app/services/reflection.py).

### Output schema (structured)

```python
class ReflectionStep(BaseModel):
    internal_draft_summary: str = Field(min_length=20)  # never shown to user
    biggest_gap: str = Field(min_length=3)              # never shown to user
    action: Literal["ask", "generate"]
    question: str | None = None                         # required if action == "ask"
```

A Pydantic validator rejects `action == "ask"` with empty `question`.

### System prompt

```
You are a tennis coaching diagnostician. Your job is to gather just enough
context to produce a personalized training plan in 4 or fewer turns.

For each turn:
1. Silently draft a tentative training plan from the conversation so far,
   anchored in the retrieved technical context.
2. Identify the SINGLE most impactful gap — a detail that, if known, would
   substantially change your draft. Examples: severity ("sails long" vs.
   "lands short"), skill level, frequency (always vs. only under pressure),
   practice context (court access, partner, wall, ball machine), time budget,
   recent attempted fix, physical limit or injury.
3. Decide: is the current draft already specific and well-supported by the
   retrieved context? If yes, set action="generate". Otherwise, action="ask".
4. If asking, produce ONE question that:
   - is plainly worded for an amateur player (no jargon unless the user used it)
   - can be answered in one sentence
   - targets the highest-impact gap, not the next obvious one
   - is NOT a repeat of anything already in the conversation
   - is NOT a yes/no question unless yes/no genuinely changes the plan
```

### User prompt (assembled per turn)

```
Conversation so far:
[user] My forehand is weak
[assistant] Does it sail long or land short?
[user] Sails long under pressure

Retrieved technical context (light, top 3):
1. [segment] Modern Forehand — windshield wiper finish: ...
2. [segment] Wrist lag — ...
3. [technical_detail] Body rotation power: ...

Turn budget: 1 of 3 questions used (2 remaining before forced generate).
Output your ReflectionStep now.
```

### Force-generate path

When `turn_count == conversation_max_turns - 1` (3 asks already done),
the user prompt appends:

```
This is your final turn. You MUST set action="generate". Do not ask another
question even if the conversation is incomplete.
```

This guarantees termination without trusting the model to count.

### Post-hoc guardrails (in `ReflectionService`, not in the prompt)

- If `action="ask"` but `question` is empty/whitespace → treat as `generate`.
- If the normalized question matches any prior assistant message (lowercased,
  punctuation stripped, stopwords removed) → retry the call once with an
  extra instruction "Your previous output repeated a prior question; ask a
  different one." If it still repeats, fall through to `generate`.
- Structured-output parse failure → retry once, then fall through to
  `generate` so we never infinite-loop.

### Why this produces high-quality questions

- Requiring `internal_draft_summary` forces the model to commit to a working
  hypothesis *before* asking — so the question is anchored in what would
  actually change the plan, not generic "tell me about yourself" filler.
- Requiring `biggest_gap` makes the model name and justify the target before
  it phrases the question.
- The one-question, no-jargon, no-shallow-yes/no rules raise information
  density per turn.
- Light retrieved context at every turn means questions are informed by what
  the actual knowledge base can address, not the model's general priors.

## 8. Final Plan Generation

[backend/app/services/llm.py](../../../backend/app/services/llm.py) and its
`generate_training_plan` method are **unchanged**. The conversation
orchestrator just hands it a richer `query` string assembled from the
transcript, e.g.:

```
Initial goal: My forehand sails long under pressure.
Clarifications:
- Frequency: only in 3rd-set tiebreaks when tired.
- Skill: 3.5 NTRP, 2 years playing.
- Practice: 2x/week, 90 min, partner + ball machine available.
```

Full RAG retrieval (`k=4`) runs against this enriched query, so the chunks
are anchored to specifics ("3rd-set fatigue", "ball sails long") rather than
the vague initial query. The existing personalization rules in the LLM prompt
finally have signal to work with. The "do not ask follow-up questions" rule
stays correct at this stage — we have committed.

## 11. Testing Strategy

- **Unit, `ReflectionService`** with a stub LLM that returns scripted
  `ReflectionStep` objects: verify prompt assembly, force-generate on last
  turn, repetition guard, parse-failure fallback.
- **Unit, `ConversationService` state machine**: start → ask → ask →
  generate; start → generate (LLM short-circuits on a detailed query);
  turn-cap hit forces generate on turn 4 even if LLM tries to ask; reply on
  a completed conversation → 409.
- **API tests** using FastAPI `TestClient` with `LLMService`,
  `ReflectionService`, and `VectorService` mocked: round-trips the
  discriminated-union response, exercises 404/409 paths.
- **CLI smoke** `python -m app.cli.chat_plan "My forehand is weak"` against
  real Gemini — manual quality pass with two or three scripted personas
  (vague query, detailed query, hostile/short answers) before declaring
  done. We inspect the persisted `reflection_meta` JSON to confirm questions
  are gap-driven rather than generic.
- **Compile check** and **migration up/down round-trip**, mirroring the
  verification already done on the existing RAG slice.

## 12. Open Risks

- **Gemini structured-output reliability**: if `with_structured_output` fails
  intermittently, the retry-then-fallback path in `ReflectionService` keeps
  the conversation alive but at the cost of skipping a question. Acceptable
  for the POC; revisit if observed often in CLI smoke.
- **Question quality drift over time**: with no eval harness, regressions in
  the reflection prompt are only catchable by manual review. The
  `reflection_meta` field is the seed for a future eval.
- **No user identity yet**: conversations are anonymous and can't be linked
  to a person. When the `User` model lands, `Conversation` needs a nullable
  `user_id` foreign key — designed to slot in without table rewrite.
